Choosing a Local Model

Open-source models pack a lot of meaning into a hyphenated file name. This guide explains every part — and what each choice means for quality, speed, memory, and tool-using agentic sessions.

Reading a model name

A model file name is a stack of tags. For example:

Qwen2.5-7B-Instruct-Q4_K_M.gguf Qwen2.5 family & version · 7B = size (7 billion parameters) · Instruct = tuned to follow instructions & use tools · Q4_K_M = 4-bit quantization (how much it's compressed) · .gguf = the llama.cpp file format

The three things that matter most are size, tuning (Instruct vs base), and quantization. The rest are modifiers. Each is covered below.

Parameters — model size (7B, 70B, 135M)

The B number is how many billion parameters (learned weights) the model has; M means millions. It is the single biggest predictor of how capable — and how heavy — a model is.

  • Bigger → broader knowledge, stronger reasoning, better at long multi-step tasks. Also slower to generate and needs more memory.
  • Smaller → fast and light, runs on modest hardware, but weaker reasoning and less reliable at complex instructions and tools.

Effective parameters — E2B, E4B. A few models (notably Google's Gemma 3n) quote an effective size: the footprint they actually run at, which is smaller than their raw parameter count thanks to tricks like Per-Layer Embeddings and the MatFormer architecture. An E4B model uses memory roughly like a 4B while drawing on more underlying capacity. (Not to be confused with A4B — see MoE below, where A = active parameters.)

Memory needed depends on size and quantization. Rough guide for a 4-bit (Q4) model plus working memory:

Size≈ RAM at Q4Good for
1–3B1–3 GBQuick chat, autocomplete, very light tools on any Mac.
7–9B5–7 GBEveryday assistant; solid tool use. The popular sweet spot.
13–14B8–11 GBNoticeably smarter; good agentic work on 16 GB+ Macs.
30–34B18–22 GBStrong reasoning; wants 32 GB+ unified memory.
70B+40 GB+Top quality; needs a high-memory Mac (64 GB+).

Rule of thumb: keep the model under ~75% of your Mac's unified memory, leaving room for the OS, the app, and the context window. AIChat warns you before loading something likely to overflow.

Quantization — how compressed it is (Q4_K_M, IQ4_XS, BF16)

Models are trained at 16-bit precision, but each weight can be quantized to fewer bits to shrink the download and memory footprint and run faster. The trade-off is a small loss of accuracy. The leading number is the bits per weight: fewer bits = smaller & faster, more bits = higher fidelity.

The letters after the number

  • _K — k-quant. A smarter scheme that spends bits where they matter most. Better quality than the old Q4_0-style "legacy" quants of the same size. Prefer k-quants.
  • _S / _M / _L / _XL — size variant. Within one bit level, Small → Medium → Large → eXtra-Large trade a little more memory for a little more quality. _M is the usual balanced pick.
  • IQ… — i-quant (importance quant). Uses a calibration dataset to preserve the most important weights, fitting more quality into very low bit-widths (great for squeezing big models in). Occasionally a touch slower on some hardware. XS/XXS are the extra-small variants.
  • UD… — Unsloth Dynamic. Unsloth's dynamic quantization keeps important layers at higher precision and compresses the rest harder, so it beats a standard quant of the same size — most noticeably at low bit-widths (e.g. UD-Q4_K_XL, UD-IQ2_M). A great way to run a larger model in less memory.

Full precision (F16, BF16, F32)

F16 and BF16 are the original 16-bit weights: top quality, but roughly 2× the memory and slower than 8-bit and ~4× the memory of a 4-bit quant. F32 is full 32-bit — maximum quality, very large, almost never needed for chat. For everyday local use a Q-quant is far lighter for nearly the same quality.

Newer float formats (MXFP4)

MXFP4 is a 4-bit floating-point "microscaling" format — a shared scale per small block of weights. It's as compact as a 4-bit integer quant but often preserves quality better, and it's increasingly used on large MoE models: MXFP4_MOE means the expert layers are stored this way. Treat it as a strong 4-bit option. (NVFP4 is a similar NVIDIA variant.)

Instruct vs. base (Instruct, Chat, -it, base)

This is easy to overlook but critical.

  • Instruct / Chat / -it: fine-tuned to follow instructions, hold a conversation, and call tools. This is what you want for chat and agentic use.
  • base / pt (pre-trained): only continues text. It won't reliably follow prompts or use tools. Use only for fine-tuning or text completion.

Context window (4k, 32k, 128k)

The context window is the maximum prompt + conversation history (in tokens) the model can consider at once. A larger window handles long documents and long agentic tool transcripts — but the key/value cache grows with context length, using more memory and slowing very long sessions. Pick more context only if you need it.

Dense vs. Mixture-of-Experts (A3B, A4B, 8x7B)

There are two ways to build a model of a given size, and the name tells you which:

  • Dense (no A… suffix): every parameter runs for every token. Smartest per parameter — best for deep reasoning and the most reliable on complex, nested tool calls — but slower and heavier.
  • Mixture-of-Experts (MoE) (A4B, 8x7B): split into many "expert" sub-networks; a router picks just a few to run per token. The A4B suffix is the active billions — e.g. 26B-A4B means 26B total but only 4B active per token. So it generates several times faster while keeping the broad knowledge of the full model.

The catch: all experts must be loaded, so an MoE uses memory like its total size, not its active size. Many MoEs also keep one small shared expert always active for general knowledge, while the routed experts specialise.

Reasoning models (R1, QwQ, Thinking)

These generate an explicit chain-of-thought before the final answer. They're markedly better at maths, coding, and multi-step planning — but slower and more verbose because they "think" in tokens first. Budget more time and context for them.

Other modifiers

  • Distill: a smaller model trained to imitate a larger "teacher" — much of the quality at a fraction of the size and speed cost.
  • VL / Vision: multimodal — also accepts images. Needs a companion projector (mmproj) file and extra memory; unnecessary for text-only chat.
  • Coder / Math: specialised for code or mathematics — great in that domain (and for coding agents), sometimes weaker at open-ended chat.
  • mini / small / medium / large: a vendor's relative size tier, not an exact parameter count. Check the explicit nB number for true size.
  • Uncensored / Abliterated: safety alignment reduced or removed, so it refuses far less. Behaviour can be less predictable; use responsibly.
  • v0.2, v1.6: the release/version — higher is usually newer and improved.

What matters for agentic sessions (models using tools)

When a model drives tools — reading files, running MCP servers, calling functions — it must repeatedly produce well-formed tool calls and reason over the results. That puts weight on different features:

A tool call is structured output (usually JSON). One missing comma or hallucinated path and the agent loop breaks — so reliability and formatting matter as much as raw intelligence.

  • Instruct-tuned is mandatory. Base models can't reliably emit tool calls. Look for Instruct/Chat. In AIChat the model list shows Tools: Supported when a model advertises a tool-calling chat template.
  • Size and reasoning help most. Multi-step plans, recovering from tool errors, and deciding when to call a tool improve sharply from ~7–8B upward, and again with reasoning models. Tiny models often loop or mis-call tools.
  • Dense vs. MoE. Dense models tend to be the most consistent on complex, deeply-nested tool calls. MoEs are much faster through long tool loops and keep broad knowledge — a well-trained agent/coder MoE is excellent, though a very low active-parameter count can occasionally make the hardest calls less reliable. Either works; favour a dense model for the trickiest tool schemas, an MoE for speed.
  • Don't over-compress. Very low bit-widths (Q2–Q3) degrade the structured-output reliability tool calls depend on. Q4_K_M or higher is a good floor for agentic work; an Unsloth UD quant is a strong choice when memory is tight.
  • Prefer recent generations. Newer model families are increasingly tuned for agentic use — stricter tool-call formatting and better cross-file/repository reasoning — so a newer version often "breaks the loop" far less than an older one of the same size.
  • Give it enough context, but mind memory. Tool transcripts (file contents, command output) fill the window fast, so prefer a larger context window — but the KV-cache grows with it. If the model + context overflows unified memory, macOS swaps to disk and speed collapses to a crawl. Keep the total under ~75% of RAM.

On Apple Silicon, AIChat runs GGUF models on Metal. Some models also ship MLX builds tuned for Apple's unified memory that can be faster — but those are a different format that this app doesn't load.
